# Garmin dashboard: project context

Personal, single-user, local-only web dashboard for my Garmin watch metrics. Data comes from Garmin's Personal API; AI insights (not built yet) come from Gemini and/or Claude. Read `PLAN.md` (phase checklist) and `docs/data-notes.md` (what the API returns, quirks, limits) before changing data code.

## Commands (uv only, never pip)
- Install / add deps: `uv sync`, `uv add <pkg>` (explain before adding a new dependency)
- Pull the last 28 days from Garmin into SQLite: `uv run python -m backend.sync [--days N]`
- Run the dashboard: `uv run uvicorn backend.main:app --reload` then open http://127.0.0.1:8000
- Run the tests (temporary database, no Garmin calls): `uv run python -m unittest`
- On the Raspberry Pi (see `docs/deploy-pi.md`): deploy with `git push pi main`; `deploy/sync-timer.sh status|on|off|at <times>|default|now` controls the scheduled sync
- Dump raw Garmin responses for exploration: `uv run python scripts/explore.py [--days N] [--only sleep hrv] [--path /x --param k=v]` (writes `raw_dumps/`, gitignored)

## Layout
- `backend/db.py`: SQLite (`data/garmin.db`, gitignored; `GARMIN_DB` in `.env` overrides the path; its folder must already exist, so an unmounted disk fails instead of starting an empty database). Tables `daily` (one row per date), `activities`, `body_battery` (one JSON curve per date), `hrv_readings` (one night's 5-minute readings per wake-up date, as minutes after that day's local midnight, negative before midnight), `run_routes` (one thinned GPS track per run, `[]` if the file has none), `tags` (one row per date and tag, entered on the dashboard), `meta` (`last_sync` is the latest attempt; `last_ok_at` is the last run that stored data). `upsert()` never overwrites an existing value with NULL. New `daily` and `activities` columns go in `ADDED_DAILY_COLS` and `ADDED_ACTIVITY_COLS`, which `connect()` adds to existing databases.
- `backend/sync.py`: pulls daily summaries, sleep summaries, HRV summaries and activities in 28-day chunks, newest first; a failing chunk is recorded in `errors` and does not stop the others. Then fetches the 5-minute HRV readings once per night that has an HRV summary (`get_daily_hrv`). Then downloads the activity file once per run (`run_details`), decodes it in memory with `garmin-fit-sdk`, and keeps only laps, HR zone boundaries, VO2 max, recovery time and the route (at most 500 points): the file also holds profile data, so it is never saved.
- `backend/export.py`: builds the compact, identifier-free JSON summary (`GET /api/export`) that I attach to AI chats for analysis.
- `backend/main.py`: FastAPI. `GET /api/daily`, `/api/activities` (every stored workout unless `limit` is given; runs also get `run`: the same fields as the export, from `run_fields()`), `/api/activities/{id}/route`, `/api/body-battery/{day}`, `/api/hrv/{day}`, `/api/tags`, `/api/status`, `/api/export`; `PUT /api/tags/{day}` (replaces the day's tags, lowercased, at most 20 tags of up to 40 characters, no future days); `POST /api/sync`; serves `frontend/`.
- `frontend/`: `index.html` (page shell), `app.js` (all the logic; most markup is built in its template strings), `style.css`. No build step; Chart.js and Leaflet from a CDN, light/dark via CSS variables. Served with `Cache-Control: no-cache` so the phone always checks for newer files. Check `node --check frontend/app.js` before pushing. Two views, switched by tabs in the header and kept in the URL (`#workouts`), or swiped between on touch screens, the other view sliding in over the current one as the finger moves, with the Range, Export and Sync controls moving as part of Graphs (left for Workouts, right for Graphs; not from charts, the map, sideways-scrolling rows or the screen edges); the range, Export and Sync controls show only on Graphs (on the phone they sit below the tabs, so the tabs never move): Graphs (sleep hero, stat row, tag log, then charts: sleep, resting HR and HRV, body battery, training load; no steps or stress charts) and Workouts (every stored workout regardless of the range, 25 at a time with Show more; the range select is hidden there): type chips, then per month a totals/averages summary and one card per workout; distance only for distance sports (`hasDistance`), since squash and HIIT pick up GPS drift. Workouts have a chip per workout type (clicking a run opens a pop-up with summary stats, route map, time in each zone, and pace, heart rate and splits per km), stress pop-up from the Average stress tile (time in each band, body battery curve), sleep pop-up from the sleep score, with arrows to step through the nights in the selected range (rating per score factor, bed and wake times, HRV status and readings through the night), HRV chart (7-day average solid, single nights dotted) shaded with Garmin's balanced range, tag log (day picker, quick-add buttons, tagged days from the first day shown), range select (7/14/28 days), Sync and Export buttons, banner for sync errors and out-of-date data. A chart tooltip hides when you tap outside the chart or tap the same day again. Below 600 px wide: phone layout (fewer workout columns, full-screen pop-ups); on touch screens Export opens the share sheet; in the home-screen app, pulling down at the top reloads the page (a deliberate 140 px pull straight down; keeps the range). `manifest.json` and the icons make it a home-screen web app.
- `tests/test_app.py`: smoke, sync and export tests.
- `deploy/`: systemd units for the Pi (dashboard, sync service and timer, templates filled in by `install.sh`), `sync-timer.sh`, and the `post-receive` hook that deploys on push.
- `scripts/explore.py`, `docs/data-notes.md` (still a stub), `PLAN.md`, `.env.example`.

## Rules
- Use Garmin's official client (`garmin_personal_api`) for every Garmin call. No hand-rolled HTTP. It handles the key-to-token exchange (tokens last 24h) and caches the token at `~/.config/garmin/`.
- Secrets live in `.env` (`GARMIN_API_KEY`, `GEMINI_API_KEY`, later maybe `ANTHROPIC_API_KEY`). Never print, log or commit them. All Garmin and AI calls happen in the backend, never in the browser.
- Garmin API is read-only. Backfill must respect per-request limits: 28 days for steps/stress, 31 for daily summaries, sleep summaries and body battery, 365 for HRV, about 45 activities per page. Daily summaries over about 90 days fail with HTTP 500. Chunk at 28 days.
- Health data stays local. Strip identifiers (name, profile ID, profile image URLs, activity names) before sending anything to an AI service, as `export.py` does. `raw_dumps/` and `data/` are gitignored. GPS routes reveal where I run, so they stay out of `/api/activities` and the export. The one deliberate exception to local-only: opening a run's pop-up requests map tiles from OpenStreetMap, which sees the area viewed and my IP, not the route.
- The dashboard runs on a Raspberry Pi at home (database on its HDD, `GARMIN_DB`), listening on 127.0.0.1 only. Phone access is through Tailscale: `tailscale serve --bg 8000` on the Pi, reachable only from my tailnet. Never Tailscale Funnel: the dashboard has no login.
- Keep changes small and simple. Update the checkboxes in `PLAN.md` as work completes.

## Data facts that matter
- Sleep rows are dated by the wake-up day. A row is partial until it is fetched after its day has ended (`summary_fetched_on`). Partial rows' steps, stress, body battery, resting HR and workouts are excluded from statistics; their sleep and HRV cover the night that just ended and are included.
- Units from Garmin: seconds (durations), metres (distance), grams (weight), epoch milliseconds (most timestamps).
- HRV baseline and status are null while Garmin is onboarding the account (status `NONE`, stored as null); they appear from 2026-11-03. HRV history starts 2026-10-16: a 365-day request returns nothing older (checked 2026-11-08). The 5-minute readings come from `get_daily_hrv(day)`, one call per night, about 80 to 100 per night.
- Not available from the Personal API: training readiness, training status, acute and chronic load, run temperature (checked 2026-11-03 via dumps, activity details, FIT files and probes). Also sleep skin temperature deviation: no client method, no temperature field in `get_daily_sleep`, sleep or daily summaries, and `skinTemp`-style paths return 404 (checked 2026-11-08, 8 nights). The watch does record it: Garmin Connect shows 'avg skin temp change', so the Personal API leaves it out. Substitutes: `activityTrainingLoad`, training effect, fitness age, resting HR, HRV, sleep score, body battery.
- VO2 max is only in each run's activity file, in undocumented message 140: field 7 / 65536 x 3.5. I confirmed the value matches my watch. Field 9 of the same message is recovery time in minutes at the end of the run: 2448 (40.8h) against about 40h on the watch for the 2026-11-08 run, one check only, so if I report a mismatch, revisit it. It includes recovery left over from earlier activities. Runs synced before it was stored are downloaded once more. `/activity-service/activity/{id}/details` has a `directPerformanceCondition` series, also not exported.
- No stress readings through the day: the client only has daily statistics, and `/wellness-service/wellness/dailyStress/{date}` returns 404 (checked 2026-11-03). Daily summaries do give time per band and max level. Closest substitute: `get_daily_body_battery(..., chunks=96)`, 15-minute readings (repeated timestamps have the same level; 28 and 31-day ranges work) plus `ACTIVITY`, `SLEEP`, `STRESS` and `RECOVERY` periods. Curves are stored in minutes after local midnight using the day's start offset, so a day with a clock change can run past 1440 and its times are an hour off after the change.
- Per-km data exists only in the activity file (`lap_mesgs`); `get_activity` has only aggregate `splitSummaries`. Run summary fields (elevation, GAP, cadence, stride, HR zone seconds) are already in `search_activities`.
- Lifestyle Logging tags entered in the Garmin Connect app are not readable: the client has no method for them, `/lifestylelogging-service/dailyLog/{date}` and similar paths return 404, and they don't appear in daily, sleep or HRV summaries (checked 2026-11-06). Tags have to be logged on the dashboard.
- Gear (shoes and their distance) is not readable either: the client has no method for it, `/gear-service/gear/filterGear` (with or without `activityId`), `/gear-service/gear/user` and `/gear-service/gear` return 404, and neither `search_activities` nor `/activity-service/activity/{id}` has a gear field (checked 2026-11-11). Gear is assigned in Connect, not on the watch, so the activity file doesn't have it. No Gear tab for now; if it's wanted before Garmin exposes it, it would have to be tracked on the dashboard, like tags.
- Sleep score factors (`daily.sleep_details`, JSON, not exported) have Garmin's rating and optimal range but no points. Only the overall score and the deep, light and REM percentages have a `value`; restlessness has no value anywhere in the summary.
- Sleep SpO2 can be null. It has been null since 2026-10-28 because Garmin returns no SpO2 at all, sleep or all-day (last reading 2026-10-27 06:29), not because of the parser; Pulse Ox is probably off on the watch. Garmin's scores (stress, body battery, sleep stages) are wrist-based estimates, not clinical values.

## Export fields (`backend/export.py`)
Only add fields; existing ones stay as they are. Anything Garmin didn't return is omitted rather than null. Paces are decimal minutes per km.
- Added to `workouts` entries for `running`, `trail_running` and `treadmill_running` only (other types keep the summary fields): `activity_subtype` (road/trail/treadmill), `primary_benefit` (Garmin's `trainingEffectLabel`, lowercased, e.g. `tempo`, `aerobic_base`), `elevation_gain_m`, `elevation_loss_m`, `avg_gap_min_per_km`, `avg_cadence_spm`, `avg_stride_length_m`, `avg_vertical_oscillation_cm`, `hr_zone_minutes` (`z1` to `z5`), `hr_zone_bounds_bpm` (zone floors, then the zone 5 ceiling), `recovery_hours_at_finish`, `hr_drift_pct`, `hr_drift_basis`, `split_type` (km/lap), `splits`.
- `splits` entries: `km` (cumulative at the end of the split), `pace_min_per_km`, `avg_hr`, `elevation_gain_m`, `elevation_loss_m`, `cadence_spm`. Laps under 50 m are left out.
- `hr_drift_pct`: first-half speed:HR divided by second-half, minus 1, by timer time. Only for runs of 40 min or more with at least 4 laps. Uses grade-adjusted pace when every lap has it (`hr_drift_basis: gap`), otherwise `pace_not_grade_adjusted`.
- `stats.runs`: `count`, `total_km`, `total_min`, `total_elevation_gain_m`, `longest_km`, `longest_min`, repeated under `last7` and `earlier`. Partial days are excluded, as in the other stats.
- `tags`: on `daily` entries for days that have any (a day with tags but no synced `daily` row is left out until a sync adds the row); top-level `tags_logged_since` is the first tagged date. Tags are free text, so they can hold identifying details: the UI asks for no names or places.
- HRV on `daily` entries: `hrv_status` (lowercased), `hrv_5min_high_ms`, `hrv_baseline_low_ms`, `hrv_baseline_high_ms` (Garmin's balanced range). The 5-minute readings are not exported.
- `readiness`: top-level series of `date` and `vo2max_estimate`, only for days with a run that has a value.
- `caveats` also covers the auto-adjusting `step_goal`, null SpO2, the unavailable metrics, and how far to trust elevation, GAP, zones and drift.
- The `trail_running` and `treadmill_running` type keys are not yet confirmed against real data: I only have `running` so far. A run that shows no `activity_subtype` means a key is wrong (`RUN_SUBTYPES` in `db.py`).

## Decisions already made
- uv for the environment; Python + FastAPI + SQLite + plain HTML/JS.
- Garmin's official client, not the third-party `gcpapi-sync` (which would add automatic range-splitting and retries but is a single-maintainer package).
- v1 metrics: sleep, resting HR, HRV, steps, stress, body battery, training load, workouts.
- Run splits come from the activity file via Garmin's `garmin-fit-sdk`, not `/details`, which is downsampled and has no laps.
- Run routes are stored locally rather than fetched on click, and drawn on OpenStreetMap tiles (decided 2026-11-04).
- Sync runs daily on the Pi from a systemd timer (default 09:00, adjustable or off with `deploy/sync-timer.sh`), plus the Sync button or CLI. It was manual while the dashboard ran on the laptop; moved to the Pi with a timer on 2026-11-08.
- Start with 28 days of data; insights explored first by attaching the export to a chat, then automated.
